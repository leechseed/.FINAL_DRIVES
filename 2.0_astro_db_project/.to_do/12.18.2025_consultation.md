## Executive Summary

**Bottom line:** The dictionary improves semantic clarity, but it also confirms a structural problem: **Layer A is not currently a pure ontology layer.** The “Narrative Definitions” frequently encode **evaluation, weighting, prominence, and usage directives**—which are not ontology-safe primitives.

**Grade:**

- **A-** as a narrative design dictionary / writer’s room spec
- **B-** as a database taxonomy intended to be normalized, queryable, and stable over time

**Primary risk:** You are asking one layer to do two incompatible jobs:

1. define concepts (ontology)
2. instruct how to deploy/weight concepts (playbook + derived outputs)

Databases hate that. It causes unclear ownership of logic, duplicated calculations, and inevitable refactors.

---

## What Changed After Reviewing the Dictionary

The dictionary does **not** relax the earlier concerns—it **strengthens** them.

The narrative definitions repeatedly contain phrases and intent like:

- “how prominent”
- “how much story weight”
- “how often and how hard you should lean”
- “numeric clue”
- “treat as their main engine”
- “scale their influence”
- “appropriate scale”
- “where you can drop shocks and twists”

Those aren’t neutral definitions. They are **operational directives** and **derived conclusions**.

So the dictionary is excellent for writers—while simultaneously proving the taxonomy is **hybridized** (ontology + playbook + scoring hooks).

## Key Findings

### Finding 1 — Layer Contamination

Your Layer A + Dictionary combination currently acts as:

- Ontology (what exists)
- Configuration (where it is in the chart)
- Interpretation (what it means)
- Evaluation (how strong / dominant / important)
- Authoring guidance (how to use it on page)

That’s not a moral failure—just a structural mismatch if the target is a production database.

---

### Finding 2 — Intrinsic vs Derived Is Blurred

The dictionary confirms that several “variables” are really **outputs** of a ruleset rather than atomic inputs.

Examples of derived-output intent:

- `HOUSE_IMPORTANCE_SCORE` → “how much story weight”
- `ASPECT_STRENGTH` → “how often and how hard you should lean”
- `DOMINANT_PLANET / DOMINANT_ELEMENT / DOMINANT_MODE` → “main vibe”
- `SHAPE_ANCHOR_PLANET` → “treat as their main engine”
- `PLANET_ESSENTIAL_DIGNITY_SCORE / PLANET_ACCIDENTAL_DIGNITY_SCORE` → “numeric clue”

**Rule:** If it’s a score, a ranking, a “dominant,” or a “most,” it is not Layer A.

---

### Finding 3 — Authoring Guidance Mixed with Definitions

Many narrative definitions are instructions for usage, not neutral concept definitions.

Examples of usage guidance (not ontology):

- “where you can legitimately drop shocks and twists”
- “how you scale their influence in group conversations”
- “the scenario you use to bring that pain back into focus”

This guidance is valuable—just not in the same layer as atomic definitions if you want a clean DB model.

---

### Finding 4 — Cross-Panel Semantic Collisions

The dictionary makes it clear that multiple panels are defining similar scene levers, which creates collisions unless you formalize precedence and relationships.

Common collision patterns:

- House “mind” vs Mercury “mind” (`H3_MIND_ARCHETYPE` vs `MERCURY_COGNITION_STYLE`)
- House “pleasure” vs Venus “pleasure” (`H5_PLEASURE_MODE` vs `VENUS_PLEASURE_METRICS`)
- House “obsession” vs Pluto “obsession” (`H8_OBSESSION_FIELD` vs `PLUTO_OBSESSION_VECTOR`)
- Sun thematic identity vs Node/MC destiny framing (`SUN_THEMATIC_QUESTION` vs `NN_*` vs `MC_*`)

These can coexist if you encode:

- which is domain-of-life vs function vs identity
- primary vs modifier
- “generates” vs “tints” vs “constrains” relationships

Right now, they read as peers.

---

### Finding 5 — Astro Coordinates Mixed with Expression

The dictionary explicitly frames some items as technical chart parameters, not narrative traits.

Example:

- `PLANET_DEGREE` → “a technical parameter for aspects and precise triggering events”

Likewise:

- sign, house, retrograde, dignity

These should be stored as **placement/geometry**, separate from **expression/meaning**, or you’ll confuse coordinates with traits throughout your system.

## Strengths Worth Preserving

- **Naming conventions are strong:** consistent prefixes, predictable structure, dev-friendly identifiers.
- **Navigation is intuitive:** Panels → Sections → Variables is a clean browse model.
- **Definitions are actionable:** as a writer’s room / prompt dictionary, it’s immediately usable.
- **Planetary subsystem segmentation is coherent:** each planet’s “lane” is relatively well-contained.

---

## Risks If You Build the DB As-Is

If you implement this as a single-layer schema without separation, expect:

- repeated logic across code paths (“is this stored or computed?”)
- inconsistent meanings for the same concept across panels
- difficult querying (because guidance and evaluation are mixed with atomic values)
- brittle joins and hard refactors once you add scoring, dominance, and synthesis rules
- unclear ownership of “truth” (definition vs output vs authoring instruction)

---

## Hard Recommendations

### Recommendation A — Split “Definition” vs “Usage Notes”

Current dictionary entries often contain usage instructions. Keep them—but move them.

For every variable, create two fields/artifacts:

1. **Definition (ontology-safe)**
   - neutral meaning
   - no weighting language
   - no “how much/how often”
2. **Usage Notes (playbook)**
   - scene levers
   - writer cues
   - when it “fires” in narrative

This single change removes the majority of future schema pain.

---

### Recommendation B — Move Rankings/Scores into Derived Outputs

All of these belong in a Derived/Computed layer, not Layer A:

- anything `*_SCORE`
- anything “dominant”
- anything “strength/importance”
- distributions, cluster counts, anchor planet, etc.

Layer A defines the concepts. Another layer computes prominence and dominance.

---

### Recommendation C — Separate Coordinates from Expression

Make it impossible to confuse these in storage:

- **Placement/Geometry:** sign, degree, house, retrograde, sect, dignity state
- **Expression/Meaning:** cognition style, love style, obsession vector, etc.

This avoids the classic failure mode: coordinates and traits being treated interchangeably.

---

## Updated Verdict

After reviewing the dictionary:

- **As a writer-facing taxonomy + prompt dictionary:** strong, coherent, close to shippable.
- **As a production database foundation:** still structurally hybridized and guaranteed to produce refactor work unless split into distinct layers.

**New condition:** Your next step should not be “more variables.”  
Your next step should be: **layer separation and classification** (atomic vs derived vs playbook).
